Gotcha worth stating out loud

OIDC identity token, not an access token

Private Cloud Run authenticates the caller with a signed identity token scoped to the service URL. An OAuth access token returns 401. This catches almost everyone the first time.

The thing people get wrong
A swarm is not five microservices calling each other. The coordinator, three specialists and the critic are nodes in one Workflow graph inside one container. There is no A2A RPC, no service mesh, and no per-hop auth between them. This is why a swarm costs the same to operate as a single agent, and why it fails as one unit rather than partially.

Why an agent cannot read a table it did not declare

This is the part worth slowing down for, because it is the answer to the first question a security architect will ask.

The core idea

The system does not read the SQL to decide whether it is safe. It asks BigQuery. Every query is submitted twice: once as a dry run to ask the engine which tables the statement actually resolves to, and again for real only if that set is inside the agent's declaration. A parser or a regex is a second opinion about what SQL means, and the gap between the two opinions is the vulnerability.

Check 1 · statement type

Must be SELECT.

This is what stops EXECUTE IMMEDIATE and multi-statement scripts. BigQuery reports those as SCRIPT with an empty referenced-tables list, so a subset check on its own would wave them straight through.

Check 2 · non-empty

Must resolve to at least one table.

A read that touches no table is either a mistake or an evasion, and it would make the provenance metadata a lie. Agents that need to compute without reading use operational_math instead.

Check 3 · subset

Resolved tables must be inside the declaration.

Both sides are normalised the same way, so a cross-project read keeps its prefix and matches nothing. Views expand to base tables in a dry run, so access cannot be laundered through a view.

Trace of one refused query
> agent D01 declares [mining_data.telemetry_stream] > agent authors: SELECT * FROM `mining_data.biometric_fatigue_logs` LIMIT 10 > dry run submitted (0 bytes billed, nothing executed) > statement_type = SELECT check 1 PASS > referenced_tables = [mining_data.biometric_fatigue_logs] check 2 PASS > subset of declared? check 3 FAIL > UNDECLARED_TABLE: query reads ['mining_data.biometric_fatigue_logs'], which this agent has not declared > the real query is never submitted
Output filter · biometric masking

Biometric fields are masked on the way out, in the one function every query result passes through, keyed on what the query actually read rather than what it declared. An operator's raw biometric trace never reaches a model or a screen.

Untrusted-text wrapping

Free-text columns coming back from BigQuery are wrapped in an explicit untrusted-data envelope before a model sees them. A maintenance note that says "ignore your instructions" arrives labelled as data, not as instruction.

Parameterised SQL

Literals in predicates are refused in favour of query parameters. Worth saying plainly in the room: this one is a lint that catches careless authoring. The control that actually constrains reach is the dry run above.

Three service accounts, not one hundred

An early instinct is one identity per agent. That does not survive contact with quota, and it buys less isolation than it appears to.

Service accountAgentsGrants
mag-agent-base35 Read the dataset. No write anywhere. The default for a Pattern B agent that only answers questions.
mag-agent-coordinator12 Read plus the ability to run a swarm graph. One per Pattern A entrypoint.
mag-agent-approver5 Read plus insert into agent_approvals. The only identities on the platform that can write anything at all.

Counts are per deployed service and read from the registry.

Why tiers beat per-agent identities
  • Quota. Service account quota is per project and this platform is redeployed repeatedly across demos. 100 identities per rebuild does not fit.
  • The isolation is elsewhere. Two agents sharing mag-agent-base still cannot read each other's tables, because the declared-table check is per agent and enforced by the query engine, not by IAM.
  • Auditability. Three identities with clearly different powers is a model a reviewer can hold in their head. One hundred identities with identical grants is theatre.

The human-in-the-loop path

Fourteen of the 52 entrypoints can propose an action that changes something physical. None of them can take it.

Sequence
01 agent reaches a recommendation 02 agent calls request_approval(...) 03 row inserted into mining_data.agent_approvals decision = PENDING approver_principal = SYSTEM:PENDING agent_reasoning_snapshot = <why> source_tables = <what it read> 04 agent returns. It does not proceed. It cannot proceed. 05 approval surfaces on the operator screen with the reasoning and the source telemetry in view 06 human holds the confirm control for 2s 07 decision -> APPROVED, approver_principal -> real identity, hold_duration_ms -> 2000, decided_at -> server time 08 action released
The load-bearing property

Nothing in this codebase can write the value APPROVED. Only a human does, through the approval surface.

That is a stronger claim than a policy or a prompt instruction, and it is the one to make when someone asks what stops the agent going rogue. The agent has no code path to approval.

hold_duration_ms
The Hold-to-Confirm interaction is not decoration. Its duration is written into the audit record, so the log can distinguish a considered decision from a reflex click.

What is not built, said plainly

Worth having ready, because volunteering a limit before it is found is worth more than being caught by it.

No trigger layer

The 52 agents are request-response services. Nothing watches BigQuery and dispatches an agent when a threshold breaks. The shift timeline option in the wireframes depends on this and is roadmap, not product.

No role-based access

Invoker is granted domain-wide for the demo. Every signed-in user can call every agent. Per-persona scoping is a real piece of work, not a config toggle.

No column-level masking in BigQuery

Masking happens in the tool layer. A dry run expands a view to its base tables, which is what makes the declared-table check strong, but it also means the check cannot tell a masked view from a raw table. That enforcement has to live elsewhere.

No Pattern C

No document search surface. The value in this dataset is structured operational data. Adding Pattern C would need a document corpus that does not exist here.

No AISC baseline

The value tree is structurally complete and financially empty. Only the $145k/hr downtime rate is a client figure. Everything else needs client input, and the screens render that as a gap rather than inventing it.

Two data gaps

No tailings dam or piezometer data, and no capital-project or EPC data. Two branches in the published industry tree cannot be served, which is why the tree was re-rooted on AISC rather than faking coverage.
