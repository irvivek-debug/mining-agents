Phase 2 · Screen Selection

Three ways to navigate 52 agents

100 agents are deployed. 52 of them are callable. The design question is not what a single agent screen looks like, it is what the operator sees before they know which agent they need. These are three answers to that question, plus the deep screens that stay the same whichever answer wins.

Why a chat box fails here
  • It hides the catalog. A reliability engineer cannot type the name of an agent they do not know exists. 52 entrypoints behind a blinking cursor is a discovery failure, not an interface.
  • It cannot show a swarm. A Pattern A run has five agents working and one critic disagreeing. A transcript flattens that into one voice, so the operator cannot tell which specialist is blocked or why.
  • It has nowhere to put an approval. Fourteen entrypoints require a human decision before anything happens. An approval needs a hold, an audit record, and the evidence in view. A message bubble has none of those.
  • It shows an answer without its inputs. In a plant, a number with no provenance is not actionable.
What every option must carry
Pattern A
Per-agent state and handoffs. The operator can tell which specialist is blocked and why.
Pattern B
The computed result and the rows it came from.
HITL
Hold-to-Confirm plus an audit trail of who approved what and when.
Device
Drawn from each persona's Journey Scaffolding. Control-room desktop, pit tablet, and plant handheld are all in scope.
Contrast
7:1 on critical telemetry. State is never carried by color alone.

Option A

The Persona Cockpit — navigate by who you are

The application opens on your role. A reliability engineer signs in and lands on reliability work, ranked by what this shift needs. The catalog is filtered to the branch you own, so 52 agents become the six or seven that are yours. Everything else is one click away but never in the way.

Strengths
  • Discovery is solved by construction. You never see an agent that is not yours.
  • Maps one-to-one onto the nine operator personas, so the Phase 0 work drives the nav directly.
  • Device profile can differ per tab, which matters because the HSE lead is on a handheld and the metallurgist is not.
Weaknesses
  • Weakest executive story. A GM sees nine tabs, not one number.
  • Cross-branch work fights the layout. A stockout that stops a work order spans supply and maintenance.
  • Needs a real role mapping in identity before it is more than a demo affordance.
Best when

The demo audience is the operating team and the buying story is adoption. This is the option that survives contact with a real shift.

Option B

The AISC Value Tree — navigate by where the money leaks

The application opens on the metric the CEO is measured on: all-in sustaining cost per tonne. Six branches hang off it, each branch carries its agents, and you drill from the money down to the specific agent that addresses it. Navigation is a cost decomposition, so every click is already an argument.

Option C

The Shift Timeline — navigate by when

The application opens on the operating day. Events land on a timeline as they happen, and each event arrives already carrying the agent that can resolve it. Nobody chooses an agent. The agent is proposed by the event, and the human decides whether to run it, approve it, or dismiss it.

Unbuilt dependency
This option needs an event bus that watches BigQuery and decides which agent an event should propose. None exists today. The 52 agents are request-response services with no trigger layer, so Option C is a larger build than A or B and cannot be demoed from the current deployment without a scripted feed.
Strengths
  • Closest to how a control room actually works. Nobody browses a catalog mid-shift.
  • Discovery disappears entirely as a problem.
  • Approvals arrive in context with the evidence already attached.
Weaknesses
  • Requires a trigger layer that is not built. Highest cost of the three.
  • Hides the catalog completely. An agent nothing ever triggers is invisible, which makes the 52 look smaller than it is.
  • No executive view at all without adding one.
Best when

The engagement continues past the demo and the customer wants the accelerator to be an operating system rather than a tool rack.

Recommendation

Ship A, open on B, keep C on the roadmap

The three options are not mutually exclusive and the demo needs two audiences served in one session. The recommendation is a single application with two entry surfaces over one shared set of deep screens.

  • Option B is the landing screen. The demo opens on AISC and the six branches, because the economic buyer is in the room for the first ninety seconds. This is the salesmanship surface.
  • Option A is the working application. One click from any branch drops into the persona cockpit that owns it. This is where the demo spends its time, and it is what a customer forking the accelerator actually runs.
  • Option C is named, not built. The timeline appears in the roadmap slide as the next increment, with the trigger layer called out as the missing piece. Naming it honestly is worth more than faking it.

The deep screens below are identical in all three options, which is what makes the hybrid cheap: the navigation model is a shell, and the expensive work is the swarm console, the workbench, and the approval surface.

Screen 3 — HITL approval surface

Fourteen of the 52 entrypoints are marked hitl_required: nine swarms (S01, S02, S04, S05, S07, S08, S09, S10, S11) and five deep agents (D07, D14, D25, D30, D37). Phase 2 makes an approval surface mandatory for every one of them, with Hold-to-Confirm and an audit trail. The rule that shapes this layout is no black-box coercion: the reasoning and the source telemetry are on screen before the human is asked to confirm.

Approval · S10 Fatigue Intervention & Stand-down Action affects a person Requested 14:25 · expires 14:55
Proposed action

Stand down operator OP-2211 for the remainder of Shift B and reassign HT-114 to the relief pool.

Why the agents recommend it
  • S10-SP1 scored fatigue in the top band for this operator across the last two hours.
  • S10-SP2 counted three microsleep events since 12:40, with the interval between them shortening.
  • S10-SP3 confirmed relief cover is available, so the stand-down does not strand the route.
  • S10-CRITIC raised no dissent.
Privacy
Biometric detail is masked in this view by the same output filter that masks it for the agents. The approver sees the score band and the event count. They do not see raw biometric traces, and the screen says so rather than leaving the absence unexplained.
Decision

This action removes a named person from duty. Hold the button for two seconds to confirm. Releasing early cancels.

Audit record · live agent_approvals schema
approval_id APR-<uuid> agent_id S10 action_type stand_down_operator target_entity OP-2211 decision PENDING -> APPROVED approver_principal <signed-in identity> decided_at <server timestamp> hold_duration_ms 2000 agent_reasoning_snapshot SP1 band, SP2 count, SP3 cover unverified_flags [] source_tables [biometric_fatigue_logs, ...] -- nothing in the codebase writes APPROVED. Only a human does, -- and hold_duration_ms is how the record proves the hold happened.
Anti-pattern check
Refuse is a plain button of equal weight, not a faint link. The confirm control is safety orange, never green. No destructive step is bundled behind a generic label: reassigning the truck is named in the action text, not hidden inside it.

Before Phase 3

Open questions and honest gaps

Unverified
  • Per-specialist observability. The swarm console assumes each specialist authors its own events in the ADK response. The probe that answers this is outstanding. If it fails, Screen 1 needs redesigning around a coordinator-only trace.
  • Role mapping. Option A assumes identity carries a persona claim. Nothing in the current deployment does that. Domain-wide invoker access was granted, so today every signed-in user can call every agent.
Client input required
  • AISC per tonne baseline, and per-branch dollar values. Only the $145k/hr mill downtime rate has been supplied.
  • Whether the operation is open pit with an on-site concentrator. The device and stress profiles behind these layouts assume it is.
  • Whether biometric masking as designed satisfies the site's union agreement. The privacy model is a process question, not only a technical one.
Not built

Option C needs an event bus that watches BigQuery and maps events to agents. No trigger layer exists. The 52 agents are request-response services today. Option C is presented as roadmap for that reason and should not be demoed as if it runs.
